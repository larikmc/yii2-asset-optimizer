# Архитектура: larikmc/yii2-asset-optimizer

## 1. Введение и цели проекта

Пакет `larikmc/yii2-asset-optimizer` предназначен для автоматической высокопроизводительной оптимизации (минификации, версионирования, обработки зависимостей) CSS и JavaScript в веб-приложениях на фреймворке Yii2.

### Ключевые требования и приоритеты
1. **Минимальные накладные расходы на HTTP-запросах (Zero-Overhead Runtime)**: Никакой сборки, обхода директорий, вызова `filemtime`, вызова Node.js/esbuild или вычисления хешей во время обработки HTTP-запроса пользователя.
2. **Надёжность и атомарность (Zero-Downtime Deployments)**: Неполная или упавшая с ошибкой сборка никогда не должна попадать в runtime. Переключение на новую версию сборки происходит атомарно.
3. **Сохранение архитектуры Yii2**: Не ломать цепочки `depends`, порядок регистрации скриптов (`POS_HEAD`, `POS_BEGIN`, `POS_END`, `POS_READY`), атрибуты тегов (`async`, `defer`, `type`, `integrity`, `nonce`), работу PJAX, AJAX и ActiveForm.
4. **Независимость от OPcache**: Обновление ассетов не должно требовать `opcache_reset()` или инвалидации кэша PHP-скриптов.
5. **Безопасный откат и очистка**: Хранение предыдущих версий, мгновенный откат без пересборки, защита активных ассетов от удаления.

## 2. Разделение Build-time и Runtime

Система строго разделена на два изолированных контура:

```
+-----------------------------------------------------------------------+
|                             BUILD-TIME                                |
| (CLI / Deployment / Watch: php yii asset-optimizer/*, Node.js, esbuild)|
+-----------------------------------------------------------------------+
      |
      | 1. Анализ зарегистрированных AssetBundle и extraFiles
      | 2. Детекция изменений (SHA-256 контента + mtime кэш)
      | 3. Минификация JS (изолированные файлы, esbuild)
      | 4. Сборка CSS (esbuild: резолвинг @import, url(), шрифты, картинки)
      | 5. Генерация контентных хешей SHA-256 (site.7a8b9c0d1e2f.min.css)
      | 6. Валидация целостности staging-сборки
      | 7. Копирование файлов в @webroot/optimized/
      | 8. Запись неизменяемого манифеста manifests/manifest-{buildId}.json
      | 9. Атомарное переключение указателя current.version / current.json
      v
+-----------------------------------------------------------------------+
|                              STORAGE                                  |
|  - @runtime/asset-optimizer/current.version (указатель активной версии)|
|  - @runtime/asset-optimizer/manifests/*.json (неизменяемые манифесты) |
|  - @webroot/optimized/* (неизменяемые публичные файлы с хешем)         |
+-----------------------------------------------------------------------+
      |
      | 1. Чтение активной версии (APCu -> pointer file)
      | 2. Получение манифеста (APCu -> decoded JSON)
      | 3. O(1) поиск в PHP-массиве: $url = $manifest[$bundle . ':' . $asset]
      | 4. Передача URL стандартному yii\web\View
      v
+-----------------------------------------------------------------------+
|                              RUNTIME                                  |
|            (HTTP-запросы пользователей: Nginx + PHP-FPM)              |
+-----------------------------------------------------------------------+
```

### Строгие запреты в Runtime:
- Запуск внешних процессов (`exec`, `proc_open`, `node`, `esbuild`).
- Регулярные выражения по готовому HTML-коду страницы (как в `skeeks/yii2-assets-auto-compress`).
- Сканирование директорий исходников (`scandir`, `glob`).
- Проверка `filemtime` на каждый файл ассета (штатный `$appendTimestamp = true` в Yii2 делает это на каждый запрос!).
- Вычисление хешей (`hash_file`, `md5`, `sha256`).
- Ожидание завершения фоновых процессов.

## 3. Анализ существующих подходов и их ограничений

### 3.1. Штатная консольная команда `yii asset`
- **Принцип**: Генерирует файл конфигурации `bundles.php` и минифицирует ассеты, объединяя их в синтетические бандлы (`all.js`, `all.css`), после чего создает PHP-файл `assets_compressed.php` с переопределениями `$assetManager->bundles`.
- **Проблемы**:
  1. *Монолитность*: Объединение всего JS сайта в один файл ломает изоляцию страниц и конфликтует с библиотеками, требующими раздельной загрузки.
  2. *Конфликт с OPcache*: `assets_compressed.php` является PHP-файлом. На production при `opcache.validate_timestamps=0` веб-сервер не видит обновлений без вызова `opcache_reset()`, что сбрасывает кэш всего приложения и вызывает падение производительности (CPU spike).
  3. *Отсутствие Watch*: Нет инкрементальной сборки и watch-режима.
  4. *Устаревший стек*: По умолчанию ориентирован на Closure Compiler / YUI Compressor через Java.
  5. *Хрупкость относительных путей в CSS*: Часто ломает пути к шрифтам и фоновым изображениям.

### 3.2. Модуль `skeeks/yii2-assets-auto-compress`
- **Принцип**: Перехватывает событие завершения рендеринга страницы (`Response::EVENT_AFTER_PREPARE_FOR_OUTPUT`), парсит сгенерированный HTML регулярными выражениями (`preg_match_all`), находит `<link>` и `<script>`, читает исходные файлы с диска, сжимает их через PHP/CLI и заменяет HTML-теги.
- **Проблемы**:
  1. *Колоссальный штраф TTFB*: При промахе кэша посетитель ждет от 1 до 5 секунд, пока PHP пережимает файлы прямо в процессе отдачи страницы.
  2. *Ненадёжность регулярных выражений в HTML*: Ломает inline-скрипты с `</script>` внутри строк, SVG-стили, conditional comments, JSON-LD schema, `<template>`.
  3. *Нарушение AJAX / PJAX*: При частичном рендеринге регулярки формируют несовпадающие наборы скриптов, что приводит к повторной инициализации событий jQuery, дублированию обработчиков и ошибкам в консоли.
  4. *Потеря атрибутов*: Сбрасывает `async`, `defer`, `nonce`, `integrity`, `data-*`.
  5. *Высокая нагрузка на CPU*: Даже при 100% попадании в кэш регулярные выражения сканируют десятки килобайт HTML на каждом HTTP-запросе.

## 4. Механизм интеграции с Yii2: `OptimizingAssetManager`

Интеграция выполняется через специализированный компонент `larikmc\assetoptimizer\OptimizingAssetManager`, расширяющий `yii\web\AssetManager`.

### 4.1. Архитектурная цепочка вызовов в Yii2
При вызове в представлении или виджете:
```php
AppAsset::register($this);
```
Yii2 выполняет:
1. `$view->registerAssetBundle($name)`
2. `$assetManager->getBundle($name)`
3. `$bundle->publish($assetManager)` (если `$sourcePath !== null`)
4. `$bundle->registerAssetFiles($view)`
5. Внутри `registerAssetFiles`:
   ```php
   foreach ($this->js as $js) {
       $file = is_array($js) ? array_shift($js) : $js;
       $options = is_array($js) ? ArrayHelper::merge($this->jsOptions, $js) : $this->jsOptions;
       $url = $manager->getAssetUrl($this, $file, ...);
       $view->registerJsFile($url, $options);
   }
   ```

### 4.2. Переопределение URL в `OptimizingAssetManager`
`OptimizingAssetManager` переопределяет метод `getActualAssetUrl($bundle, $asset)` и `getAssetUrl($bundle, $asset, $appendTimestamp = null)`.

#### Формирование ключа ресурса
Для исключения коллизий одинаковых имен файлов (например, `css/site.css` в нескольких бандлах или `main.js`) формируется составной логический ключ:
```php
$key = get_class($bundle) . ':' . ltrim($asset, '/\\');
// Пример: 'frontend\assets\AppAsset:css/site.css'
// Пример: 'yii\web\YiiAsset:yii.js'
```
Также поддерживается вторичный ключ по относительному пути источника от webroot/sourcePath для динамических файлов.

#### Логика разрешения:
```php
public function getAssetUrl($bundle, $asset, $appendTimestamp = null)
{
    if (!$this->enabled) {
        return parent::getAssetUrl($bundle, $asset, $appendTimestamp);
    }

    $key = $this->buildAssetKey($bundle, $asset);
    $optimizedUrl = $this->manifestRegistry->resolveUrl($key);

    if ($optimizedUrl !== null) {
        // Ресурс оптимизирован: URL уже содержит контентный SHA-256 хеш!
        // Никогда не дергаем filemtime() на запросе.
        return $optimizedUrl;
    }

    // Если ресурс исключен или не входит в сборку — штатный фоллбэк
    return parent::getAssetUrl($bundle, $asset, $appendTimestamp);
}
```

### 4.3. Решение проблемы избыточной публикации из `sourcePath`
В стандартном Yii2, если у бандла задан `$sourcePath` (например, вендорные бандлы `yii\web\YiiAsset`, `yii\bootstrap5\BootstrapAsset`), метод `$bundle->publish($am)` копирует каталог из `vendor/` в `@webroot/assets/<crc32>/`.

**Решение в `OptimizingAssetManager`**:
1. В build-time оптимизатор обходит зарегистрированные бандлы, читает файлы из их `$sourcePath`, минифицирует их и публикует напрямую в `@webroot/optimized/`. Все связанные картинки и шрифты также компилируются esbuild и кладутся в `@webroot/optimized/assets/`.
2. В runtime: если бандл полностью оптимизирован (все его `css` и `js` присутствуют в манифесте), `OptimizingAssetManager` в переопределенном методе публикации предотвращает дисковые операции копирования для полностью управляемых бандлов, при этом полностью сохраняя штатную публикацию для сторонних, динамических и исключенных бандлов.

### 4.4. Поддержка `View::registerJsFile()` и `View::registerCssFile()`
Для скриптов, подключаемых напрямую во `View` минуя `AssetBundle`:
- В конфигурации оптимизатора поддерживается секция `extraFiles`:
  ```php
  'extraFiles' => [
      '@webroot/js/custom-inline-helper.js',
      '@webroot/css/extra.css',
  ]
  ```
- Оптимизатор предоставляет хелпер `Optimizer::url('@webroot/js/custom-inline-helper.js')` или алиасное сопоставление в `OptimizingAssetManager::resolveAsset()`.
- Никакой regex-замены готового HTML не применяется, соблюдая принцип предсказуемости и безопасности.

### 4.5. Поддержка Subresource Integrity (SRI)
Если бандл или приложение использует атрибут `integrity`:
- esbuild/PHP вычисляет SHA-384 хеш от итогового минифицированного содержимого файла.
- Манифест содержит секцию `integrity`:
  ```json
  "integrity": {
      "frontend\\assets\\AppAsset:css/site.css": "sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  }
  ```
- При регистрации файла опция `integrity` автоматически подменяется на актуальную для минифицированного файла, предотвращая сбои браузерной валидации.

## 5. Минификация и обработка зависимостей через esbuild

### 5.1. JavaScript: политика изоляции (Zero-Bundling для традиционных скриптов)
По умолчанию для существующих скриптов Yii2 **не включается bundling и code-splitting**.
- **Причина**: В экосистеме Yii2 многие скрипты рассчитывают на глобальные переменные (`var yii = ...`, `window.jQuery`, глобальные функции валидаторов ActiveForm, виджетов PJAX).
- **Режим esbuild**:
  ```bash
  esbuild input.js --minify --sourcemap=external --target=es2018 --outfile=output.<hash>.min.js
  ```
  Это гарантирует:
  1. 100% сохранение глобальных областей видимости и сторонних плагинов.
  2. Исключение случайного превращения в ES-модули (`type="module"`), которое ломает обычные скрипты.
  3. Сохранение порядка выполнения скриптов, заданного в `depends` и `$view->registerJsFile()`.

### 5.2. CSS: обработка зависимостей и относительных путей
Для CSS esbuild запускается в режиме бандлинга зависимостей файла:
```bash
esbuild input.css --bundle --minify --loader:.woff2=file --loader:.woff=file --loader:.ttf=file --loader:.svg=file --loader:.png=file --loader:.jpg=file --asset-names=assets/[name].[hash] --public-path=/optimized/ --outfile=output.<hash>.min.css
```
**Преимущества esbuild для CSS**:
1. Автоматический резолвинг локальных `@import` с сохранением каскада.
2. Автоматический пересчет и переписывание путей в `url(...)`: относительные пути к шрифтам и фоновым изображениям корректно перенаправляются на `/optimized/assets/[name].[hash].[ext]`.
3. Валидация зависимостей: если CSS ссылается на несуществующий файл (ошибка 404), esbuild прерывает сборку с фатальной ошибкой. Ошибочный манифест не активируется.
4. Внешние URL (`http://`, `https://`, `//`, `data:`) остаются нетронутыми.

## 6. Инкрементальная сборка и Watch-режим

### 6.1. Инкрементальная детекция изменений
Оптимизатор ведет кэш сборки `@runtime/asset-optimizer/build-cache/cache.json`:
- Для каждого исходного файла и его выявленных зависимостей сохраняется:
  - `mtime` (первичная быстрая проверка);
  - `sha256` содержимого (строгая проверка при несовпадении mtime);
  - Результирующий контентный хеш выходного файла;
  - Версия esbuild и флаги сборки.
- Если исходные файлы и их зависимости не изменились, выходной файл повторно используется без вызова esbuild.
- Если итоговый набор выходных файлов совпадает с активным релизом — новый манифест не публикуется.

### 6.2. Режим Watch
- Запускается отдельным процессом: `php yii asset-optimizer/watch`.
- Построен на базе esbuild context watch либо отслеживания файловой системы с задержкой группировки (debounce 150 мс).
- Алгоритм при сохранении файла разработчиком:
  1. Группировка событий сохранения (150 мс).
  2. Инкрементальный запуск сборки только затронутых цепочек.
  3. Проверка результата.
  4. При ошибке: вывод в консоль понятного сообщения об ошибке (с указанием строки и файла). Активный манифест **не изменяется**, сайт продолжает работать на последней валидной сборке.
  5. При успешном исправлении ошибки: автоматическая атомарная активация нового манифеста.
  6. Браузер при обновлении страницы мгновенно получает актуальные URL с новыми хешами.

## 8. Атомарная активация и поддержка Windows / Linux

### 8.1. Алгоритм активации сборки
1. **Блокировка**: Захват неблокирующей эксклюзивной блокировки файла `@runtime/asset-optimizer/.build.lock` через `flock($fp, LOCK_EX | LOCK_NB)`. Если сборка уже идет, повторный процесс сообщает о занятости и завершается.
2. **Сборка во временной директории (Staging)**:
   Файлы компилируются в `@runtime/asset-optimizer/staging/{buildId}/`.
3. **Проверка (Verify)**:
   - Анализ кода возврата и stderr esbuild.
   - Проверка наличия всех файлов из списка на диске и их ненулевого размера.
   - Сверка SHA-256 контента созданных файлов с хешами в staging-манифесте.
4. **Перемещение в релизное хранилище**:
   - Новые файлы копируются из staging в `@webroot/optimized/`. Поскольку имена содержат контентный хеш, они гарантированно не перезаписывают и не повреждают текущие активные файлы.
   - Неизменяемый манифест сохраняется в `@runtime/asset-optimizer/manifests/manifest-{buildId}.json`.
5. **Атомарное переключение указателя (Switch)**:
   - В Linux: запись во временный файл `current.version.tmp` с последующим атомарным `rename('current.version.tmp', 'current.version')`.
   - В Windows: стандартный вызов `rename()` завершается с ошибкой, если целевой файл существует. Для Windows реализуется двухфазная безопасная замена: запись во временный файл, безопасная замена через замену/атомарное чтение, гарантирующая, что читающий процесс никогда не прочитает полупустой файл.
6. **Освобождение блокировки**: `flock($fp, LOCK_UN)`.

## 9. Управление кэшем, OPcache и APCu

### 9.1. Идеальное кэширование в браузере и CDN
Все файлы в `@webroot/optimized/` содержат контентный хеш в имени. Для них в конфигурации веб-сервера (Nginx) настраивается максимальный срок жизни:
```nginx
location /optimized/ {
    expires 365d;
    add_header Cache-Control "public, max-age=31536000, immutable";
    access_log off;
    try_files $uri =404;
}
```
При любом изменении CSS/JS меняется контентный хеш в имени файла и ссылка в HTML. Браузер мгновенно скачивает новый файл без ожидания истечения TTL.

### 9.2. Полная независимость от OPcache
- Мы **не используем** файлы `.php` для хранения манифестов и маппинга ассетов.
- Манифест хранится исключительно в `.json`.
- Функция `json_decode(file_get_contents(...))` не кэшируется в OPcache bytecode cache.
- Следовательно, обновление ассетов **никогда не требует `opcache_reset()`** даже при `opcache.validate_timestamps=0`!

### 9.3. Многоуровневое чтение манифеста в Runtime
1. **Уровень 1 (In-Memory per Request)**:
   В рамках одного жизненного цикла HTTP-запроса разобранный манифест хранится в приватном свойстве `OptimizingAssetManager`. Все последующие вызовы `getAssetUrl` работают с памятью (0 дисковых обращений).
2. **Уровень 2 (APCu Cache — при наличии)**:
   - Проверяется ключ `apcu_fetch('asset_optimizer:build_id')`.
   - Если ключ совпадает, манифест извлекается из `apcu_fetch('asset_optimizer:manifest:' . $buildId)`.
   - Если в APCu ничего нет или указатель обновился, читается файл `current.version`, загружается `manifest-{buildId}.json`, сохраняется в APCu.
3. **Уровень 3 (File System — если APCu отсутствует)**:
   - Читается компактный файл `current.version` (несколько байт, мгновенно отдается из page cache ОС).
   - Читается и декодируется `current.json`.

## 10. Сохранение версий, Rollback и Prune

### 10.1. Сохранение старых версий
Старые версии файлов в `@webroot/optimized/` **не удаляются** в момент активации новой сборки:
- Пользователи с открытыми вкладками сайта продолжают запрашивать старые хешированные CSS/JS без ошибок 404.
- Активация новой версии происходит без задержек.

### 10.2. Команда отката (`rollback`)
```bash
php yii asset-optimizer/rollback [buildId]
```
1. Если `buildId` не указан, команда показывает список доступных исторических манифестов с датой сборки и количеством файлов.
2. Проверяет физическое наличие всех файлов из выбранного манифеста в `@webroot/optimized/`.
3. Атомарно переключает `current.version` на выбранный `buildId`.
4. Откат происходит за несколько миллисекунд без повторной компиляции.

### 10.3. Безопасная очистка (`prune`)
```bash
php yii asset-optimizer/prune --keep=5 --days=30 [--dry-run]
```
1. Очистка запускается исключительно по крону или при деплое, но никогда на HTTP-запросах.
2. Алгоритм:
   - Собираются все активные манифесты последних `N` сборок (`--keep=5`), а также все сборки моложе `D` дней (`--days=30`).
   - Формируется белый список (whitelist) всех используемых в них файлов и зависимостей (шрифты, SVG).
   - Сканируется директория `@webroot/optimized/`.
   - Файлы, не входящие в белый список и созданные ранее порогового времени, удаляются (или выводятся в отчете `--dry-run`).
   - Ни один активный или защищенный файл гарантированно не удаляется.

## 11. Поддержка Yii2 Advanced (Frontend / Backend)

В структуре Yii2 Advanced разные приложения имеют собственные webroot (`frontend/web` и `backend/web`).
Оптимизатор поддерживает:
1. Изолированные пространства имен и конфигурации:
   - `frontend`: манифесты в `@frontend/runtime/asset-optimizer/`, файлы в `@frontend/web/optimized/`.
   - `backend`: манифесты в `@backend/runtime/asset-optimizer/`, файлы в `@backend/web/optimized/`.
2. Консольная команда поддерживает ключ `--app=frontend` или отдельные команды для каждого веб-приложения:
   ```bash
   php yii asset-optimizer/build --app=frontend
   php yii asset-optimizer/build --app=backend
   ```

## 12. Консольный интерфейс CLI

Команды реализуются в контроллере `larikmc\assetoptimizer\commands\AssetOptimizerController`:

| Команда | Описание |
|---|---|
| `php yii asset-optimizer/build` | Инкрементальная сборка измененных ассетов |
| `php yii asset-optimizer/build --full=1` | Полная принудительная пересборка с очисткой кэша сборки |
| `php yii asset-optimizer/watch` | Фоновое отслеживание файлов и мгновенная пересборка для dev-окружения |
| `php yii asset-optimizer/verify` | Проверка целостности активной сборки, валидация файлов и хешей |
| `php yii asset-optimizer/stats` | Подробная статистика: экономия размера, время сборки, список ассетов |
| `php yii asset-optimizer/rollback` | Откат на предыдущую стабильную сборку |
| `php yii asset-optimizer/prune` | Очистка устаревших ассетов с защитой активных версий |
| `php yii asset-optimizer/doctor` | Диагностика окружения: проверка Node.js, esbuild, прав на запись, APCu, OPcache |

## 13. План тестирования и критерии готовности

### 13.1. Модульные и функциональные тесты (PHPUnit)
- Корректная генерация ключей ресурсов для бандлов с `sourcePath` и без него.
- Валидация JSON-схемы манифеста.
- Работа `OptimizingAssetManager`:
  - с включенным оптимизатором (подмена URL на хешированные);
  - с выключенным оптимизатором (прозрачный фоллбэк);
  - с частично оптимизированными бандлами;
  - поведение при отсутствующем ключе в манифесте.
- Атомарное переключение указателя (тесты на блокировки и перезапись в Windows и Linux).
- Инкрементальный кэш: пропуск неизмененных файлов.
- Prune: сохранение защищенных версий и удаление осиротевших файлов.

### 13.2. Тестирование сборок esbuild
- Минификация CSS с относительными путями (`url(fonts/...)`).
- Минификация JS без превращения в модули и с сохранением глобальных объектов.
- Обработка синтаксических ошибок в исходниках (сборка прерывается, active manifest не затронут).

### 13.3. Локальное интеграционное тестирование на `rb-new.loc`
- Проверка всех ключевых страниц: главная, категории, раскраски, страницы с AJAX/PJAX, формы, ЛК.
- Проверка отсутствия ошибок 404 в Network tab браузера и ошибок в Console.
- Бенчмарк времени отклика: сравнение TTFB и времени рендеринга шаблонов до и после подключения.
